## 1. 产品定位

**面向中小型景区的 AI 数字人导览 SaaS**。景区管理方通过后台一次性配置景区资产与知识库，游客扫码即得一个会说话、认路、懂景区的 AI 导游。

### 1.1 双端定位

| 端 | 用户 | 核心价值 | 形态 |
|------|------|------|------|
| 游客端 | 到场游客，零安装 | 随时能问、走到哪讲到哪、想去哪带路 | 手机 H5（扫码进入） |
| 管理后台 | 景区运营人员，非技术 | 配置能落地、内容能维护、效果能看见 | PC Web |

### 1.2 产品边界

**做**：单景区内的导览、讲解、问答、路线、运营分析
**不做**：票务交易、酒店预订、社交内容、跨景区聚合平台

### 1.3 商用形态的三条底线

判断"是否可商用"只看三件事，任何一条不满足即不可交付：

1. **不能有假数据** —— 管理后台每一个可见入口，要么连真后端，要么不存在。演示态数据是产品事故。
2. **不能有死路** —— 每一条路由、每一个按钮都有真实结果。占位页不是功能。
3. **核心链路可自证** —— 游客问答、语音交互、路线导览、围栏播报在无人工干预下端到端跑通。

|------|------|------|

| scenic | 景区资产 / 地图版本 / 围栏定义 / 标签 | **地图版本是唯一事实源**，节点与连线归本域 |

| system | 认证 / RBAC / 配置中心 / 操作日志 / 限流 | 补齐后三项 |

### 2.3 三条架构不变量

违反任何一条即视为架构劣化：

1. **地图版本是唯一事实源** —— 游客端看到的景点、路径、围栏，必须来自 `status=ONLINE` 的地图版本。AI 不得编造任何不在该版本内的节点。
2. **AI 上下文与导览状态分离** —— 对话历史由 ChatMemory 维护；AI 需要"我在哪、去过哪"时，通过 Tool 主动查询 tourist 域，而非把状态塞进 prompt。
3. **analytics 只读** —— 分析域永不反向修改业务数据。

## 4. 关键设计裁定

以下六项是本次接手需要做出的架构决策，逐条给出选择与理由。

### 4.1 ASR 方案：服务端阿里云 NLS

**选择**：前端 `MediaRecorder` 采集 → 上传后端 → 阿里云 NLS 一句话识别 → 文本进入现有问答链路

**理由**：
- 浏览器 `SpeechRecognition` 在国内 Android/微信 WebView 支持极差，不可依赖
- NLS 凭证已配置、TTS 已跑通同一套 SDK，边际成本最低
- 识别文本落库便于 analytics 复用

**接口**：`POST /api/v1/tourist/guide/asr` → `{ text }`

**降级**：识别失败明确回落到文字输入，不静默失败。

**落地注记**（2026-07-27）：

- **SDK 选型**：用已引入的 `nls-sdk-transcriber`（实时识别）做一句话识别——整段 WAV 一次 `send` 后 `stop`，`onSentenceEnd` 拼最终文本。没有为此再引 `nls-sdk-asr`
- **格式转换在前端**：`MediaRecorder` 产出 webm/opus，NLS 只认原始 PCM/WAV 流，因此 `utils/audioWav.js` 用 Web Audio 解码 → 混单声道 → 线性重采样 16k → 手工封 WAV 头。后端只做 magic 头校验（RIFF/WAVE），不做转码
- **前端形态**：按住说话（Pointer Events，触屏鼠标通用），60 秒自动停，松手即识别，识别文本**填入输入框而非直接发送**——游客确认后再发，误识别可改。过短录音（<2KB）按误触处理
- **回落路径全覆盖**：无 `getUserMedia`（非安全上下文）、麦克风拒绝、上传失败、空识别——四种失败都明确提示并引导打字，不静默
- **`listening` 态同步接通**：录音期间 `avatarState='listening'`，结束回到 `thinking`/`idle`，状态机最后一态闭环

### 4.2 对话历史：补 GET 接口

**选择**：`GET /api/v1/tourist/guide/sessions/{id}/messages?page&pageSize`

数据已完整落在 `tourist_message`，只是缺一个读接口。前端进入会话时拉取最近 N 条渲染。上限复用既有配置 `tourist-message-history-limit: 100`。

> 这是**投入产出比最高的一个修复**：一个查询接口 + 一次前端调用，直接消除"刷新即失忆"这一最伤体验的缺陷。

### 4.3 假数据页面：接真后端，不下架

**选择**：为 5 个 mock 模块补齐后端（标签 / 角色 / 权限 / 操作日志 / 限流），`/system/configs` 直接改接已有配置中心接口，随后**删除 `resourceConfigs.js` 与 `GenericAdminPage.vue`**。

**理由**：这五项都是商用 SaaS 的刚需（多人协作要 RBAC、出事要查日志、对外要限流），下架等于砍功能。真正要消灭的是"假装有功能"这件事本身，而非功能。

> `GenericAdminPage` 这个抽象本身不坏，坏在数据源写死。但为 5 个结构差异明显的资源硬套一套通用表格，收益低于维护成本，改造时按页面独立实现更清晰。

### 4.4 route 域重建

route 域当前只有 1 个只读接口，与 CLAUDE.md 承诺严重不符。重建方案：

| 能力 | 方案 |
|------|------|
| 预置路线维护 | **存储不拆表**（与景点、路网同处草稿 payload，随地图版本原子发布），仅管理入口从 scenic 的 `map-drafts/{id}/preset-routes` 迁至 route 域 `PUT /api/v1/admin/routes/preset/{draftId}`（权限 `route:write`），写入仍委托 scenic 草稿服务——拆表会把"发布地图"与"发布路线"拆成两次写入，中间态让游客拿到指向旧节点的路线 |
| 点对点算路 | Dijkstra 已实现（`ScenicTopologyPathService`），补齐加权选路并激活 `route-dijkstra-weight-*` 三个权重配置 |
| 拓扑导览推进 | 会话新增 `route_node_seq` 游标，到点（50 米抵达半径）推进并触发到站讲解，与围栏冷却互通防重复播报 |
| AI 路线生成 | 保持现有 Agent Tool 方案，**不改**（已含节点合法性校验） |

**关于节点存储**：当前节点与连线在 `scenic_map_draft.payload` JSON 内。Dijkstra 只需在算路时从 ONLINE 版本读取一次并在内存建图，**不必为此拆表**——保持地图版本的原子性比关系化更重要。若后续统计需要，再补物化视图。

**关于算法归属（2026-07-26 定档）**：CLAUDE.md 把"Dijkstra 路径"列在 route 域职责下，但算法实现留在 scenic 域的 `ScenicTopologyPathService`，**这是有意为之而非欠账**：

- 它遍历的是 scenic 拥有的地图 payload，搬到 route 等于把 scenic 的内部结构暴露出去
- scenic 的 `ScenicMapPublishService` 在发布前要调用它做连通性校验；若算法在 route，会形成 `scenic → route → scenic` 循环依赖

裁定是**拆策略而非拆算法**：权重策略归 route（`RouteWeightProvider` 读配置中心），算法与图遍历留 scenic，权重值以 `RouteWeights` 记录传入，scenic 因此不反向依赖 route。

**关于代价与里程分离**：加权后的 Dijkstra 累计值掺入了耗时与拥挤度，**不再是真实米数**。选路用加权代价，里程与耗时另行沿选中路段累加真实标注值——否则导览会对游客播报错误距离（`TouristGuideService` 的"已按当前发布路网计算 X 米"直接取这个数）。

**关于设施作为带路终点（2026-07-27 定档）**："带我去洗手间"这类诉求的终点是设施，而设施不是路网节点（图只含景点与路线端点）。不把设施升格为节点——那要求工作台为每个设施维护连线，录入成本远超收益。定档为**最近路网节点 + 尾段直线**：`resolveDestination` 先按景点精确/模糊匹配，再按设施名称/类型/口语别名（内置短别名表：洗手间/厕所/wc→卫生间、餐厅/吃饭→餐饮）匹配，命中后按 Haversine 选最近路网节点跑 Dijkstra，尾程按直线距离折算（75 米/分）累加进总量，`message` 如实告知"先到「X」再步行约 N 米"。路径可视化同步补一个不带路线编号的尾段几何点，让高亮折线画到设施位置。设施无坐标时宁可报"没有找到终点"也不编造直线。

### 4.5 测试分层：三层定档，标签隔离

盘点后确认纯逻辑已全部在离线层（§4.5 初版要迁的围栏/坐标/路线/Dijkstra/权限均已离线化），剩余 `@SpringBootTest` 类按真实依赖分两层，用 JUnit Tag 标注（常量 `common/TestTags`）：

| 层 | 覆盖 | 依赖 | 运行方式 |
|------|------|------|------|
| **离线单测**（默认层，不标注） | 纯逻辑：围栏状态机、坐标转换、路线校验、Dijkstra、权限判定、词云、问答召回、配置服务逻辑 | 无（mock Mapper/Redis） | `mvn test`，进 CI |
| **集成测试** `@Tag("integration")` | 请求管线全链路（MockMvc + 真实切面 + Redis 会话）、ConfigService 缓存与 yaml 兜底、RedisUtils | Spring 容器 + Testcontainers（MySQL 8.0 用 `sql/init.sql` 建库 + Redis 7.4），只需 Docker | `mvn test` 默认包含（4 类 36 条，基类 `AbstractIntegrationTest`） |
| **外部调用** `@Tag("external")` | 真实 NLS/OSS/LLM/Qdrant 连通性与音质验证 | 真实云服务与密钥 | **`mvn test` 默认排除**，`mvn test -Pexternal-tests` 启用（8 类 23 条） |

**原则**：纯逻辑不许起 Spring 容器；外部调用不许拖垮默认构建（慢、烧云配额、依赖网络），但保留一键验证真实连通性的入口。surefire 用 `surefire.excludedGroups` 属性控制，`external-tests` profile 置空即全量。

**外部依赖 Mock 化**（应用本身可带 mock 跑）属路线图 P2-3，不在本层定档范围。Testcontainers 化已落地（P2-2）。

### 4.6 RBAC：权限码在代码，角色在数据库

初版计划是 `sys_role` / `sys_permission` / `sys_user_role` 三张表，权限点也做成可增删的数据。**否掉了权限点落表**。

**理由**：权限码的唯一意义是"某个接口会校验它"。后台能自由新增的权限码没有任何接口认识它，只是个空壳；反过来，删掉一个代码里正在校验的权限码，会让接口静默变成谁都进不去。权限码必须和注解同源，因此定义在 `system.security.PermissionCode` 枚举里——17 个码，按 7 个模块分组，后台只读展示、只做勾选。**角色才是数据**：

| 表 | 用途 |
|------|------|
| `sys_role` | 角色本体，`builtin=1` 的内置角色不可删 |
| `sys_role_permission` | 角色 ↔ 权限码勾选，**物理删除** |
| `sys_user_role` | 管理员 ↔ 角色分配，**物理删除** |

两张关联表不走全局逻辑删除：逻辑删除会让"取消勾选后重新勾选"撞上唯一键。

**四条实现约束**：

1. **权限集不进 Token**。JWT 只带身份，权限集每次请求按 userId 查（Redis 缓存 + DB 兜底）。代价是每请求一次缓存读，换来的是改授权立刻生效，不必等 Token 过期或强制下线。
2. **两层门槛，不互相覆盖**。`@RequireAdmin` 管"是不是后台用户"，`@RequirePermission` 叠在上面管细粒度。后者**不参与**"方法级注解覆盖类级"的判定——否则方法上的权限码会把类上的 `@RequireAdmin` 顶掉，门槛不升反降。切面内另有一道 `role == ADMIN` 复核：游客和管理员的 userId 来自不同的表，数字会撞车，不复核就等于把管理员的权限借给了同号游客。
3. **提权路径只留给 root**。角色的增删改、账号的增删改一律 `@RequireRoot`：能改角色 ≡ 能给自己加任意权限，能建账号并配角色同理。下放给权限码的只有读操作（`system:role:manage` / `system:user:manage`）。
4. **前端菜单只是回显**。菜单按 `GET /admin/users/me` 下发的权限码过滤，目的仅是少让人点到 403；root 拿到全量码，保证菜单永远不比接口更严。真正的门在切面上。

内置角色（系统管理员 / 内容运营 / 只读观察员）开机自动补种，只在角色标识缺失时补，不覆盖管理员已调整的勾选；补种失败只告警不阻断启动——root 账号本身不依赖角色，权限体系可以在系统起来后再修。

### 4.7 操作日志：自动兜底 + 注解增强

后台写操作必须全部留痕。纯注解式（每个写接口手标 `@OperationLog`）漏标一个就是审计空洞；纯自动式又太干（只有 `PUT /api/v1/admin/roles/3` 这类原始路径）。定档为**结构保证完整性，注解只补可读性**：

- `OperationLogAspect` 捕获 `/api/v1/admin/**` 下全部非 GET 请求——新接口忘了标注也照样进日志
- `@OperationLog` 是可选增强：中文模块名/动作名（缺失时取 Swagger `@Tag` → 类名、方法名前缀 → HTTP 方法逐级推导）、`withoutParams`、`ignore`，以及把登录这类非 admin 前缀接口拉入记录范围

**四条实现约束**：

1. **切面排在 `AuthAspect` 外层**（`@Order(1)` 对无 `@Order` 的最低优先级）：越权被拒的请求以异常形式穿过日志切面，记成 FAILURE。"谁试图删了不该删的东西"比成功记录更有审计价值，漏掉它等于只审计守规矩的人
2. **参数落库前过三道**：跳过不可序列化的容器对象（用 `instanceof` 判 `ServletRequest` 等——容器传进来的是 `RequestFacade`，包名比对会漏网）、递归按字段名脱敏（密码/验证码/密钥全打码，手机号保头尾）、按 `ops-operation-log-param-max-length` 截断（默认 2000 字符，防大 payload 把审计变成事故源）
3. **审计绝不弄坏业务**：组装与落库两级 try/catch 吞异常只告警，开关读不到默认继续记。写入同步执行——后台写是人工点击频率，一条索引化 INSERT 远比会丢记录的异步队列可靠
4. **日志只读不可改、过期物理删**：没有编辑接口是有意的，能改的审计记录等于没有审计。`sys_operation_log` 刻意不带 `deleted` 字段（逻辑删除等于永不释放磁盘），每日 03:20 定时任务按 `ops-operation-log-retention-days`（默认 90 天）物理清理；**配成 0/负数视为永久保留不删**，避免误配清空审计。读权限下放给 `system:log:read`（第 17 个权限码），手动清理限 root

### 4.8 标签：词表是数据，引用是 code

标签初版计划只有"`scenic_tag` 表 + CRUD + 页面"——但那样做出来的是一个**没有消费者的死 CRUD**，和被删掉的 mock 页只有真假之分。定档为三段闭环：

1. **词表是数据**：`scenic_tag`（code / name / color / description / status），全局共享不挂景区，后台 CRUD 维护
2. **引用是 code**：地图草稿的 `SpotDraft.tags` 存 code 列表，随地图版本原子发布（与 §4.4 预置路线同一取舍——景点的一切定义都在 payload 里）。名称与颜色在展示时按 code 回填，**改词表名不破坏已发布地图**
3. **agent 是消费者**：`inspectScenicMap` 与 `searchScenicResources` 把解析后的中文标签名透给 LLM，"带孩子玩什么"这类偏好因此能匹配到挂"亲子"标签的景点

**三条实现约束**：

1. **code 建后不可改**，与角色标识同理——它是草稿 JSON 里的稳定引用。唯一性由服务层在未删除行内保证，不用数据库唯一键：逻辑删除的行会永久占住 code，复合唯一键又会在"建-删-建-删"的第二次删除时撞键
2. **删除不做引用检查**：引用散落在各地图草稿的 JSON payload 里，查不全也查不准。删除/停用后旧 code 在解析时自然落空，前端与 agent 一律按"查不到即不展示"处理
3. **词表故障不拖垮 agent**：工具工厂解析标签时吞异常降级为空标签——词表是增强信息，不能成为问答链路的单点

### 4.9 接口限流：规则是配置，计数在 Redis

遵守 §5 的既定裁决"限流不建表"：规则以 JSON 数组存在配置中心 `ops-rate-limit-rules`（name / pattern / methods / limit / windowSeconds / enabled），后台"限流配置"页做结构化编辑，底层复用配置中心读写接口，不新增专用 CRUD。

**机制**：`RateLimitFilter` 注册在 `JwtAuthFilter` 之后，命中 Ant 路径模式的请求按固定窗口计数——窗口号 = 当前秒数 / 窗口时长，计数 key 含规则名 + 身份 + 窗口号，原子 INCR，首次自增时设过期，窗口滚动自然清理。

**四条实现约束**：

1. **身份选择**：已认证按 JWT subject 计数（同一办公网出口的多个管理员不共享配额），匿名按 `X-Forwarded-For` 首跳 IP
2. **叠加规则全部要过**：命中多条规则时逐条计数，任何一条超限即拒。先命中先过会让"全局限流 + 登录专项限流"的组合形同虚设
3. **三级故障全部放行**：开关配置读不到按开启、规则 JSON 解析失败按空规则、Redis 故障按放行。限流是保护性措施，任何一级出问题都不能反过来阻断业务
4. **429 与业务错误码同构**：超限直接由过滤器写 `ApiResponse` JSON（`code=RATE_LIMIT`），不进入 Controller，前端按普通错误提示即可

默认种子三条：认证接口 10 次/分/IP、游客写 30 次/分/身份、后台写 60 次/分/身份。短信发送在 `AuthService` 里另有业务级频控（60s/10min/日三档），两者互补：过滤器挡的是刷接口，业务频控挡的是烧短信费。

### 4.10 词云与情感分析：词表锚定，采样封顶

**词云**（A10）定档为两层算法，不引入 NLP 分词依赖——游客提问是短口语问句，词表锚定已覆盖主要信号：

1. **领域词表锚定**：已发布地图的景点名、设施名与设施类型、启用标签名逐条在样本中计数。运营最关心"游客在问哪些点"，这一层信号最强，来源标为 SPOT/FACILITY/TAG
2. **中文二元组滑窗**：捕捉词表之外的热词（如"夜景"），用停用字表（的了是吗呢…）、频次 ≥2、同字重复过滤压噪声；已被任何领域词包含的二元组去重，避免"书院"既算领域词又算热词。来源标为 NGRAM

样本取时间区间内**最新 5000 条**游客消息（`messageCount` 单独 count，不被截断影响），Top 30 按权重出榜。领域词表或标签服务故障时降级为纯二元组统计——只读分析接口不能因为词表坏了而 500。前端是纯 CSS span 云（字号按权重缩放、颜色按来源区分），与看板既有手绘图表同风格，不引 echarts。

**情感分析**激活死配置 `analytics-sentiment-batch-size`（默认 100）：正则粗分（投诉/疑问/满意三组特征）从"区间内全表扫描"封顶为最新 N 条，配置读不到回落默认值。正则只是 MVP 占位，LLM 情感分类留作 P2 候选——届时同一配置项控制送样批量，语义不变。

### 4.11 向量检索：可选增强，故障降级

复核（P1-16）证实 Qdrant 长期零接线：切片 `vector_status=DONE` 是本地假标记，检索一直是纯关键词 n-gram。关键词兜不住"语义问法不匹配关键词"（游客问"哪里有凉快的地方"，切片写的是"林荫步道"），这是商用 RAG 的核心召回痛点，定档补齐为**可选增强**：

1. **默认关闭**：`qa-vector-enabled` 默认 false，关闭时部署不需要 Qdrant 与 embedding，检索为纯关键词——部署依赖不新增。`QaVectorService` 用 ObjectProvider 注入双 bean，缺 bean 或开关关闭即全局 no-op
2. **写路径**：reindex 时真 embedding（`text-embedding-v4`，维度由 `qa-vector-dimension` 对齐）写 Qdrant，点 id = 切片 id，payload 带 `doc_id` / `scenic_area_id`；collection 缺失时按维度自动建（Cosine）。删除文档同步按 `doc_id` 过滤清理向量点，失败仅告警
3. **检索合并**：向量命中在前（语义相关性），关键词命中按分补位、按切片 id 去重，入上下文上限不变；召回宽度与相似度阈值由既有配置 `qa-rag-top-k` / `qa-rag-similarity-threshold` 激活控制
4. **故障降级**：检索路径任何异常（Qdrant 挂、embedding 超时）返回空，自然退化为纯关键词——向量是增强不是单点；写路径失败抛 `VectorIndexException`，如实标 FAILED 但不阻断重建（切片落库后仍可关键词检索）
5. **`vector_status` 语义修正**：SKIPPED（开关关闭未向量化的正常态）/ DONE（已写入）/ FAILED（写入失败），是真实的向量索引状态而不再是装饰字段；关键词检索不再以它为过滤条件（历史上那个恒真过滤是假标记的伴生品）

### 4.12 无密钥演示部署：外部依赖全部可降级

商用交付要求"新克隆 + 只配数据库和 Redis 就能完整演示"。盘点启动与运行期的外部依赖后定档：**LLM / TTS / ASR / OSS / Qdrant 全部可缺省，降级行为显式、可观测、不吞真实故障**。

1. **LLM 可缺省**：`spring.ai.model.chat` / `embedding` 由环境变量 `APP_AI_CHAT_MODEL` / `APP_AI_EMBEDDING_MODEL` 驱动（默认 openai）。置 `none` 后 `API_KEY_CHAT` / `API_KEY_EMBEDDING` 不再被要求；Spring AI 的 ChatClient 自动装配仍强制要求容器存在 ChatModel，故注册 `UnavailableChatModel` 占位（任何真实调用显式报错）。`QaChatStreamService` 经 ObjectProvider 双注入识别占位后**降级为检索证据直出**：FAQ/RAG 检索到的已确认内容直接作答，evidence 标 `LLM_OFF`；工具调用（AI 路线规划、点对点算路）与多轮记忆在该部署形态下不可用
2. **TTS 可缺省**：`dh-tts-provider=mock` 或 NLS 密钥未配置（NlsClient 未装配）时，`SilentWavGenerator` 本地生成 16k 单声道静音 WAV——前端"音频 + 字幕"链路完整可演示，缓存实体的格式字段如实标 `wav`（不沿用 profile 的 mp3，避免前端解码错）
3. **ASR 可缺省**：`dh-asr-provider=mock` 或 NlsClient 未装配时返回空串，前端按既有"没听清"提示引导文字输入
4. **bean 装配条件化**：`AliyunNlsConfig` / `AliyunOssConfig` 的客户端 bean 用 `@ConditionalOnExpression` 判密钥非空白才装配（`@ConditionalOnProperty` 对空串也判命中，是已踩过的坑）；NLS 启动不再真实申请 token。OSS bean 主代码本就零消费者（仅外部连通性测试使用），条件化后无密钥不再卡启动
5. **降级只发生在"密钥从未配置"**：bean 缺省 = 密钥空白，此时降级；密钥配置了但调用失败（网络、配额、参数）仍然显式报错——真实故障不会被静默吞掉，与 §4.11 向量降级的边界一致

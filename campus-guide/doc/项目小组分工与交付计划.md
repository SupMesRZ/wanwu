## 地图工作台与草稿上线链路

> 本节保留分工口径。地图草稿、预置路线、知识库资料和游客端读取规则以 `doc/地图草稿与内容关系定稿.md` 为准。

### 业务目标

负责后台地图工作台从前端编辑到真实后端保存、校验、上线的完整链路。

地图工作台的核心价值是维护景区空间拓扑，不承担完整内容管理职责。

### 涉及页面

| 页面 | 目标效果 |
|---|---|
| `/scenic/map-workbench` | 运营维护多个地图草稿、景点、服务点、路线段、polygon、路线端点、中间路径点和预置路线 |
| `/scenic/map-publish` | 展示草稿校验、阻塞项、提醒项，并把某个草稿切换为 ONLINE |
| `/scenic/areas` | 管理单景区基础资料、默认中心点、默认缩放 |

### 涉及表

| 表 | 用途 |
|---|---|
| 地图草稿相关表 | 同一景区多个草稿，只允许一个 ONLINE |
| 草稿工作台数据 | 保存景点、服务点、内部地图点、路线段、预置路线、地图中心点和默认缩放 |
| 草稿上线记录 | 记录草稿上线操作，不做回滚和历史版本 |

### 待实现功能

#### 地图工作台接口

```text
GET /api/v1/admin/map-drafts
POST /api/v1/admin/map-drafts
GET /api/v1/admin/map-drafts/{draftId}/workbench
PUT /api/v1/admin/map-drafts/{draftId}/workbench
```

要求：

- 工作台只编辑当前选中的地图草稿
- 当前阶段暂不做多景区，默认使用“桃花源”作为内部景区上下文
- `ONLINE` 草稿禁止编辑物理拓扑，允许热更新运营元信息
- `DRAFT` 草稿允许完整编辑
- 保存草稿不直接影响游客端
- 草稿 payload 固定为：

```json
{
  "spots": [],
  "facilities": [],
  "routeEndpoints": [],
  "routeSegments": [],
  "presetRoutes": []
}
```

#### 发布接口

```text
GET /api/v1/admin/map-drafts/{draftId}/publish-check
POST /api/v1/admin/map-drafts/{draftId}/publish
```

要求：

- 发布页基于运营选择的草稿做校验
- 存在 error 级阻塞项时拒绝发布
- 发布成功后目标草稿变为 `ONLINE`
- 原 `ONLINE` 草稿自动变为 `DRAFT`
- 同一景区只允许一个 `ONLINE` 草稿
- 游客端只读取 `ONLINE` 草稿

#### 发布校验

至少包含：

| 校验项 | 级别 |
|---|---|
| 景区默认中心点缺失 | error |
| 景点 polygon 无效 | error |
| 路线缺少起点或终点 | error |
| 路线起终点相同 | error |
| 路线引用对象不存在 | error |
| 启用预置路线引用不存在景点 | error |
| 启用预置路线相邻景点不可达 | error |
| 内部地图点孤立 | warning |
| 景点没有关联路线 | warning |
| 路线长度为空 | warning |
| 路线耗时为空 | warning |
| AI 描述为空 | warning |
| 路线停用或严重拥挤 | warning |

## 跨成员接口契约

### 地图草稿契约

游客端和其他域读取地图数据时，统一读取 `ONLINE` 地图草稿：

```text
map_draft.status = ONLINE
```

草稿数据结构：

```json
{
  "spots": [],
  "facilities": [],
  "routeEndpoints": [],
  "routeSegments": [],
  "presetRoutes": []
}
```

禁止游客端读取普通 `DRAFT` 草稿。

### 景点内容契约

景点基础描述放在地图草稿中，作为 AI 理解空间对象的轻量说明。

讲解词、视频、音频、长文档不放在景点对象中。QA 内容域只维护景区级资料，不绑定景点、服务点、路线或地图草稿。

### 路线内容契约

路线只保留空间和推荐相关轻描述：

```text
length_meter
duration_min
route_type
is_paid
crowd_level
ai_note
```

路线不保存完整讲解词，不保存视频素材。

### 数字人播报契约

QA 负责给出文本，digitalhuman 负责把文本转成声音或播报资源。

```text
text -> digitalhuman tts -> audio_url
```

### 游客位置契约

游客位置统一使用项目默认坐标系 `gcj02`。

后台地图使用高德 JSAPI，游客端地图展示使用手绘地图，但围栏判断和路线计算都使用当前 `ONLINE` 地图草稿中的坐标数据。

## 10. 协作规则

### 10.1 禁止事项

- 禁止恢复旧的 `scenic_node/scenic_edge/scenic_fence` 模型
- 禁止把内部地图点做成运营资产
- 禁止让游客端读取地图草稿
- 禁止把讲解词、视频素材塞进 `scenic_spot`
- 禁止在路线几何编辑时隐式拆分路线
- 禁止在 system 域写业务规则

### 10.2 接口先行

每个成员开始开发前，必须先提交：

- 表设计
- DTO 契约
- 接口路径
- 页面交互草图或字段说明
- 验收用例

### 10.3 最小可验收粒度

每个任务按一个页面或一个业务闭环交付，不按零散函数交付。

推荐粒度：

```text
页面能打开
列表能加载
表单能提交
数据库能落表
刷新后数据仍在
错误能提示
```

mvn clean compile

```

前端：

```

核心接口需要至少有：

## 11. 当前优先级结论

当前最优先的是负责的地图发布主链路。原因：

- 其他域都需要稳定的景区和 `ONLINE` 地图草稿作为基础数据
- 游客自动导览必须读取 `ONLINE` 地图草稿
- QA 内容按景区维护，不绑定景点 ID
- AI 路线推荐需要稳定的 route_segment 图谱

因此短期分工应保持：

```text
：地图工作台和草稿上线
知识库与 QA 负责人：知识库和讲解内容
数字人与语音负责人：数字人和 TTS
游客会话与自动导览负责人：游客会话和围栏触发
```

这套分工可以最大限度减少相互阻塞，也能保证每个人都有明确可验收页面和数据表。

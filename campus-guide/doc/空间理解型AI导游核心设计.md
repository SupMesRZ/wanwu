# 空间理解型 AI 导游核心设计

> 本文描述当前空间能力如何服务 AI 数字人导游。当前设计以景点 polygon、服务点点位、内部地图点和路线段为核心

## 1. 定位

本项目不是自研城市级导航，也不替代高德、百度等导航产品。后台维护的路线图谱服务三个目标：

1. 让 AI 能理解景区内景点、服务点和路线之间的空间关系
2. 支撑游客端手绘地图上的路线高亮和导览推进
3. 支撑基于地理围栏的自动讲解和路线推荐理由生成

## 2. 当前空间对象

| 对象 | 数据来源 | 作用 | 是否运营可见 |
|------|----------|------|--------------|
| 景区 | `scenic_area` | 地图中心、默认缩放、景区基础信息 | 是 |
| 景点 | `scenic_spot` | 游览目标、讲解目标、围栏触发来源 | 是 |
| 景点 polygon | `scenic_spot.fence_polygon` | 自动讲解围栏、范围展示、标注点中心 | 是，作为景点的一部分 |
| 服务点 | `scenic_facility` | 卫生间、游客中心、停车场、商店等服务目标 | 是 |
| 内部地图点 | `route_endpoint` | 空白路线端点、分叉端点 | 否，只在绘制/重设端点时辅助显示 |
| 路线段 | `route_segment` | 两个端点之间的一段可通行关系 | 是 |
| 中间路径点 | `route_segment.middle_points` | 折线形状控制点 | 否，只在编辑路线时显示 |

## 3. 为什么不做完整导航

景区 AI 导游需要的是“可解释的游览路线”，不是转弯级导航。完整导航需要道路网、实时定位纠偏、map matching、方向角、导航语音和道路合规数据，这会把项目带向 GIS 导航系统。

本项目选择人工维护路线段：

- 运营可以表达桥、坡、临水、缆车、收费、拍照点等 AI 需要的语义
- 游客端可以在手绘地图上看懂路线
- AI 推荐可以读取路线长度、耗时、拥挤度和描述信息
- 地理围栏讲解可以围绕景点 polygon 触发，而不是围绕复杂道路网触发

## 4. 路线图谱

路线图谱由 `route_segment` 构成。每条路线段连接两个端点：

```text
端点 = SPOT | FACILITY | ENDPOINT
路线段 = from + to + middlePoints + routeAttributes
```

示例：

```text
A 景点 -> B 景点
```

保存为一条路线段：

```json
{
  "from": { "type": "SPOT", "id": 1 },
  "to": { "type": "SPOT", "id": 2 },
  "middlePoints": [[30.2524, 120.1380], [30.2530, 120.1400]],
  "lengthMeter": 520,
  "durationMin": 8,
  "routeType": "WALK",
  "paid": false,
  "aiNote": "平整石板路，适合亲子和老人慢行"
}
```

分叉示例：

```text
        -> B
A -> J -> C
        -> D
```

保存为四条路线段：

```text
A -> J
J -> B
J -> C
J -> D
```

其中 `J` 是 `route_endpoint`，不是景点或服务点。

## 5. 算路策略

route 域把 `route_segment` 转换成图：

- 图顶点：`SPOT:{id}`、`FACILITY:{id}`、`ENDPOINT:{id}`
- 图边：启用状态的 `route_segment`
- 边权重：长度、耗时、拥挤度、收费、routeType、AI 描述中的语义标签

基础权重：

| 维度 | 数据来源 |
|------|----------|
| 距离 | `route_segment.length_meter` |
| 耗时 | `route_segment.duration_min` |
| 拥挤度 | `route_segment.crowd_level` |
| 可通行 | `route_segment.status` |
| 收费 | `route_segment.is_paid` |
| 语义信息 | `route_segment.ai_note` |

AI 推荐不是只求最短路。推荐逻辑应综合游客偏好、时长、景点标签、服务点需求、路线属性和拥挤度。

## 6. 地理围栏自动讲解

围栏来源是景点 polygon：

```text
scenic_spot.fence_polygon -> 游客位置判定 -> 进入/停留/离开事件 -> 自动讲解
```

判定规则：

1. 游客端或后端获得游客位置
2. 查询当前景区启用景点 polygon
3. 判断位置是否进入 polygon
4. 根据会话状态、防重播和冷却时间决定是否触发讲解
5. 触发后记录围栏日志和讲解状态

服务点默认不触发讲解，除非后续业务明确需要。

## 7. 后台地图工作台

后台工作台只展示运营关心的对象：

- 景点
- 服务点
- 路线
- 发布状态

交互规则：

- 新建景点：点击地图创建标注点和默认 polygon
- 编辑景点 polygon：拖动顶点后自动回写景点范围，并更新标注点到几何中心
- 拖动景点：polygon 整体平移，关联路线端点跟随
- 新建服务点：点击地图创建点位
- 拖动服务点：关联路线端点跟随
- 新建路线：点击景点、服务点、已有内部端点或空白地图点作为头尾，沿途打中间路径点
- 编辑路线：默认只改中间折线形状，不自动重绑端点
- 重设端点：运营显式点击“重设起点/终点”后才执行端点吸附和重绑

## 8. 发布校验

发布页至少校验：

| 校验项 | 级别 | 说明 |
|--------|------|------|
| 景点 polygon 有效 | error | polygon 至少 3 个有效坐标点 |
| 路线头尾存在 | error | from/to 必须存在 |
| 路线头尾不同 | error | 不允许自环路线 |
| 内部地图点被引用 | warning | 未被路线引用的 endpoint 应清理 |
| 景点关联路线 | warning | 启用景点没有路线时提醒 |
| 路线属性完整 | warning | 长度、耗时、AI 描述为空时提醒 |
| 停用路线 | warning | 停用路线不参与游客端推荐 |
| 严重拥挤路线 | warning | crowdLevel >= 5 时提醒运营确认 |

## 9. 游客端展示

游客端不接后台高德地图编辑能力。游客端读取已发布的手绘地图、景点、服务点、路线折线和推荐结果：

- 地图底图：手绘地图
- 路线展示：高亮 polyline
- 景点展示：手绘地图上的图标或编号
- 自动讲解：基于景点 polygon 判定，不要求游客看到 polygon

## 10. AI 使用方式

AI 不直接编造路线。AI 需要通过工具查询结构化数据：

- 景点列表和标签
- 服务点列表
- route_segment 图谱
- route_segment 属性和 AI 描述
- 当前游客会话位置和偏好

AI 的输出应解释路线原因，例如：

- 这条路耗时较短
- 中途经过卫生间和游客中心
- 避开拥挤路线
- 适合老人，因为坡度描述较少且耗时短
- 适合拍照，因为 route 的 AI 描述含临水、桥景、观景点

## 11. 当前不做

- 不做城市级导航
- 不做路线中间点吸附
- 不让运营单独管理内部地图点
- 不维护独立节点/连线 CRUD
- 不维护独立围栏 CRUD
- 不在几何编辑时隐式拆分路线
